# Controller protocol

Controller packets between the Clear XR visionOS client and `clearxr-layer`, carried on Clear XR's Foveated Streaming message channel. The client sends one controller packet per rendered frame. The layer sends a haptic packet whenever the game applies or stops a vibration.

Golden byte vectors for every packet type live in `vectors.json`, generated by `generate_vectors.py`. Both implementations test against them; see [Golden vectors](#golden-vectors).

## Channel

| | |
|---|---|
| UUID, as visionOS reports it | `78563412-3412-3412-1234-56789ABCDEF0` |
| Raw bytes, in order | `78 56 34 12 34 12 34 12 12 34 56 78 9A BC DE F0` |

Both sides use the 16 raw bytes as listed: Foundation's `UUID(uuidString:)` on visionOS, and the `XrUuidEXT` byte array on the PC. They are the in-memory form of the Windows `GUID` `{12345678-1234-1234-1234-56789ABCDEF0}`, because a `GUID` stores its first three fields little-endian.

The channel also carries the client's stream configuration packets: magic `0x4346` ("CF"), a little-endian u32 JSON length, then UTF-8 JSON. The layer applies them to the CloudXR runtime's settings. Receivers dispatch on the magic.

## Conventions

- Integers are little-endian. Floats are IEEE 754 binary32, little-endian.
- In version 2, every field sits at its natural alignment and every packet size is a multiple of 8, so plain C structs (no packing pragma) and Rust `#[repr(C)]` structs match the layouts. Implementations should assert the sizes.
- **Times** are headset monotonic time in nanoseconds: the clock behind `CACurrentMediaTime()` and ARKit anchor timestamps, converted as `UInt64(seconds * 1_000_000_000)`. The PC cannot relate them to its own clock; only differences between two headset times are meaningful there.
- **Head frame**: the ARKit `DeviceAnchor` frame at the hand's `sampleTimeNs`. Meters, +X right, +Y up, −Z forward, the same axes as OpenXR `VIEW` space. The device anchor need not sit at the eye centroid OpenXR uses for `VIEW`, so the origins may differ by a few centimeters. The layer applies a constant `headOffset`, the device anchor's position in `VIEW` space, which is zero until end-to-end testing measures it.
- Quaternions are stored x, y, z, w and are unit length.
- Senders write reserved fields and reserved bits as zero. Receivers ignore them.

### Receiving

A receiver reads the 16-bit magic at offset 0 and hands configuration packets to their own handler. For the packets in this document it reads the version at offset 2, then:

1. Rejects a packet shorter than 4 bytes.
2. Rejects the packet if the magic is wrong, the version is not 2, or the packet is shorter than that version's size.
3. Ignores bytes past that version's size, and ignores reserved fields and bits.
4. Rejects a haptic packet whose `hand` or `command` is not a defined value.
5. Treats a hand whose pose or velocity fields contain NaN or infinity as having no valid pose.

Any layout change gets a new version number; nothing is appended to an existing version.

## Controller packet (client → layer)

Magic `0x5343`. Both sides implement version 2 only.

### Version 2 (248 bytes)

Header:

| Offset | Size | Type | Field |
|---:|---:|---|---|
| 0 | 2 | u16 | `magic` = 0x5343 |
| 2 | 1 | u8 | `version` = 2 |
| 3 | 1 | u8 | `activeHands`: bit 0 left, bit 1 right, bits 2–7 reserved |
| 4 | 2 | u16 | `flags` |
| 6 | 2 | u16 | reserved |
| 8 | 4 | u32 | `sequence` |
| 12 | 4 | u32 | reserved |
| 16 | 8 | u64 | `sendTimeNs`: when the client built the packet |

Left hand block at offset 24, right hand block at offset 136, each 112 bytes:

| Offset | Size | Type | Field |
|---:|---:|---|---|
| 0 | 8 | u64 | `sampleTimeNs`: the time the pose describes |
| 8 | 2 | u16 | `buttons` |
| 10 | 2 | u16 | `trackingFlags` |
| 12 | 4 | u32 | reserved |
| 16 | 8 | f32 × 2 | `thumbstick` x, y in [−1, 1]; +x right, +y pushed away from the user |
| 24 | 4 | f32 | `trigger` in [0, 1] |
| 28 | 4 | f32 | `grip` in [0, 1] |
| 32 | 12 | f32 × 3 | `gripPose.position` |
| 44 | 16 | f32 × 4 | `gripPose.orientation` |
| 60 | 12 | f32 × 3 | `aimPose.position` |
| 72 | 16 | f32 × 4 | `aimPose.orientation` |
| 88 | 12 | f32 × 3 | `linearVelocity`, m/s |
| 100 | 12 | f32 × 3 | `angularVelocity`, rad/s |

`activeHands` marks the hands with a connected controller. The block of a hand whose bit is clear is ignored; senders fill it with zeros and identity orientations.

`flags`:

| Bit | Name | Meaning |
|---:|---|---|
| 0 | `HEAD_RELATIVE` | Poses and velocities are in the head frame. Version 2 senders always set it. A clear bit is reserved for poses in the remote-scene frame (the immersive-space pose transformed by the inverse of `immersiveSpaceFromRemoteSceneTransform`); a layer that doesn't support it treats both hands as having no valid pose. |
| 1–15 | reserved | |

`sequence` increases by one per packet and wraps at 2³². The client may start at any value. The layer accepts the first packet it sees whatever its sequence, and forgets the last accepted value whenever it opens or reopens the channel and after 100 ms without an accepted packet. Otherwise a packet is newer when `(int32)(sequence − last) > 0`, computed with wrapping arithmetic (Rust `seq.wrapping_sub(last) as i32 > 0`, Swift `Int32(bitPattern: seq &- last) > 0`); the layer drops older and duplicate packets.

`sampleTimeNs` is the anchor timestamp, or the target time when the client predicts the pose forward. It may be later than `sendTimeNs`. The difference `sampleTimeNs − sendTimeNs` tells the layer how far ahead (positive) or behind (negative) the pose was when sent; compute it as a wrapping 64-bit subtraction read as signed (Rust `sample.wrapping_sub(send) as i64`, Swift `Int64(bitPattern: sample &- send)`).

`gripPose` and `aimPose` are the controller's OpenXR grip and aim poses expressed in the head frame. `linearVelocity` and `angularVelocity` are the grip pose's velocity relative to the world (not relative to the head), expressed in head-frame axes at `sampleTimeNs`. That is what OpenXR reports as `XrSpaceVelocity` once rotated into the runtime's frame. The aim pose's linear velocity is `linearVelocity + angularVelocity × (aimPose.position − gripPose.position)`, and its angular velocity is `angularVelocity`.

ARKit's `AccessoryAnchor.velocity` and `angularVelocity` describe the anchor origin in the anchor's own axes. The client converts them: `ω_world = R_anchor · angularVelocity` and `v_grip_world = R_anchor · velocity + ω_world × (p_grip − p_anchor)`, then rotates both into head axes with `R_headᵀ`.

`trackingFlags`. Bits 0–3 equal OpenXR's `XrSpaceLocationFlags`, so the layer can copy them:

| Bit | Name |
|---:|---|
| 0 | `ORIENTATION_VALID` |
| 1 | `POSITION_VALID` |
| 2 | `ORIENTATION_TRACKED` |
| 3 | `POSITION_TRACKED` |
| 4 | `LINEAR_VELOCITY_VALID` |
| 5 | `ANGULAR_VELOCITY_VALID` |
| 6 | `LOW_ACCURACY` |
| 7–15 | reserved |

From ARKit's `AccessoryAnchor.TrackingState`: `positionOrientationTracked` sets bits 0–5; `positionOrientationTrackedLowAccuracy` sets bits 0–6; `orientationTracked` sets bits 0 and 2, and may also set bit 1 when the position fields hold the last known position; `untracked` sets none. If the device anchor at `sampleTimeNs` is unavailable or untracked, the client sets none of bits 0–6; if it is only orientation-tracked, the client clears bits 1 and 3. The last known position is the last tracked world position re-expressed in the head frame at `sampleTimeNs`. A connected but untracked hand still reports its buttons.

`buttons`. The bits name the OpenXR Oculus Touch inputs they drive. Which PSVR2 button feeds each bit is the client's choice: the Clear XR client maps GameController's `Button A` to bit 0 and `Button B` to bit 1 on both hands.

| Bit | Name | Left hand | Right hand |
|---:|---|---|---|
| 0 | `BUTTON_A` | `x/click` | `a/click` |
| 1 | `BUTTON_B` | `y/click` | `b/click` |
| 2 | `TRIGGER` | trigger pressed | trigger pressed |
| 3 | `GRIP` | squeeze pressed | squeeze pressed |
| 4 | `THUMBSTICK_CLICK` | `thumbstick/click` | `thumbstick/click` |
| 5 | `MENU` | `menu/click` | none in Touch; layer-defined |
| 6 | `TOUCH_BUTTON_A` | `x/touch` | `a/touch` |
| 7 | `TOUCH_BUTTON_B` | `y/touch` | `b/touch` |
| 8 | `TOUCH_TRIGGER` | `trigger/touch` | `trigger/touch` |
| 9 | `TOUCH_GRIP` | squeeze touched | squeeze touched |
| 10 | `TOUCH_THUMBSTICK` | `thumbstick/touch` | `thumbstick/touch` |
| 11–15 | reserved | | |

Oculus Touch's `thumbrest/touch` has no bit, because PSVR2 Sense has no thumb rest; the layer reports it as false. Bits 0–10 have the same meaning in version 1.

### Hand state on the layer

A hand is connected while the layer has accepted a packet in the last 100 ms (on the layer's clock) and that packet has the hand's `activeHands` bit set. Connection changes, interaction-profile events, and pass-through to the runtime follow only this rule. While a hand is connected, the layer serves its buttons and axes from the latest packet, copies `trackingFlags` bits 0–3 into `XrSpaceLocationFlags` and bits 4–5 into `XrSpaceVelocityFlags`, and reports no valid or tracked flags (rather than passing through) while bits 0–3 are clear.

A client that stops sending, because the session paused or disconnected, sends nothing more; both hands go stale after 100 ms.

### Composing poses on the layer

To locate a bridge action space at time T, the layer:

1. Locates `VIEW` in the requested base space at T with `XrSpaceVelocity`: rotation `R_v`, position `p_v`, velocities `v_v` and `ω_v`.
2. Rotates the hand's velocities into base axes: `v = R_v · linearVelocity`, `ω = R_v · angularVelocity`.
3. Extrapolates the head-relative pose over `Δt = (T − receive time) + (sendTimeNs − sampleTimeNs)`, capped at 100 ms, using the velocities relative to the head expressed in head axes: `ω_rel = R_vᵀ (ω − ω_v)` and `v_rel = R_vᵀ (v − v_v − ω_v × (R_v · gripPose.position))`. Receive time is the layer's `XrTime` when the packet arrived.
4. Applies `headOffset` and composes the result with `VIEW` at T.
5. Reports `v` and `ω` (or the aim velocities above) as the space's `XrSpaceVelocity`.

### Version 1 (100 bytes)

The `SpatialControllerPacket` earlier Clear XR clients sent, kept for reference. Neither side implements it: the layer rejects version 1, so an older client's controllers go unanswered until it updates. Its layout is packed, not naturally aligned.

| Offset | Size | Type | Field |
|---:|---:|---|---|
| 0 | 2 | u16 | `magic` = 0x5343 |
| 2 | 1 | u8 | `version` = 1 |
| 3 | 1 | u8 | `activeHands`: bit 0 left, bit 1 right |
| 4 | 48 | | left hand |
| 52 | 48 | | right hand |

Hand (48 bytes): `buttons` u16, reserved u16, `thumbstick` f32 × 2, `trigger` f32, `grip` f32, `position` f32 × 3, `orientation` f32 × 4 (x, y, z, w).

## Haptic packet (layer → client)

Magic `0x4856`. Both sides implement version 2 only.

### Version 2 (24 bytes)

| Offset | Size | Type | Field |
|---:|---:|---|---|
| 0 | 2 | u16 | `magic` = 0x4856 |
| 2 | 1 | u8 | `version` = 2 |
| 3 | 1 | u8 | `hand`: 0 left, 1 right |
| 4 | 1 | u8 | `command`: 0 apply, 1 stop |
| 5 | 1 | u8 | reserved |
| 6 | 2 | u16 | reserved |
| 8 | 8 | u64 | `durationNs`: 0 means the shortest vibration the controller can play |
| 16 | 4 | f32 | `frequency` in Hz: 0 means unspecified |
| 20 | 4 | f32 | `amplitude` in [0, 1] |

The layer maps OpenXR's `XR_MIN_HAPTIC_DURATION` to `durationNs` 0 and `XR_FREQUENCY_UNSPECIFIED` to `frequency` 0. A stop packet sets `durationNs`, `frequency`, and `amplitude` to zero, and the client ignores them.

An apply replaces any vibration playing on that hand, and an apply with `amplitude` 0 is a stop. The layer maps any duration of zero or less to `durationNs` 0. The client caps durations at 10 seconds (which also covers `XR_INFINITE_DURATION`), clamps `amplitude` to [0, 1], treats a non-finite `frequency` or `amplitude` as 0, and stops all vibration when the channel closes, the session pauses or disconnects, or that hand's controller disconnects.

### Version 1 (20 bytes)

The `HapticEventPacket` earlier Clear XR layers sent, kept for reference; neither side implements it. Its `durationNs` is not 8-byte aligned.

| Offset | Size | Type | Field |
|---:|---:|---|---|
| 0 | 2 | u16 | `magic` = 0x4856 |
| 2 | 1 | u8 | `version` = 1 |
| 3 | 1 | u8 | `hand`: 0 left, 1 right |
| 4 | 8 | u64 | `durationNs` |
| 12 | 4 | f32 | `frequency` |
| 16 | 4 | f32 | `amplitude` |

Version 1 has no stop command.

## Golden vectors

`vectors.json` holds an array of vectors. Each has a `name`, a `type` (`controller` or `haptic`), the packet as `hex`, and one of:

- `fields`: the decoded values. A decoder must produce exactly these, and an encoder given these values must produce exactly `hex`, unless the vector has `"decodeOnly": true`. Every float in the vectors is exactly representable in binary32, so comparisons are exact. Field names match this document.
- `reject`: why the packet is malformed. A decoder must reject it.

The client tests its controller encoder and its haptic decoder. The layer tests its controller decoder and its haptic encoder.

The client's packet code, `ClearXR/Models/ControllerBridgePacket.swift` in the clearxr-visionos repository, depends only on Foundation and simd, so a Mac compiles it with a small driver and checks it:

```sh
clearxr-layer/protocol/check_swift.sh ../clearxr-visionos/ClearXR/Models/ControllerBridgePacket.swift
```

The layer's tests run with `cargo test` in `clearxr-layer`.

To change a layout, edit this document and `generate_vectors.py` together, then run:

```sh
python3 clearxr-layer/protocol/generate_vectors.py          # rewrite vectors.json
python3 clearxr-layer/protocol/generate_vectors.py --check  # confirm it is current
```
